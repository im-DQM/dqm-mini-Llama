## 2. 测量方法

所有对比都遵循同一套控制变量流程：

1. 同一个二进制、同一个模型、同一 prompt / seed / n_predict / threads，一次只改 matmul mode。
2. 正式测量前先跑一轮 warmup。
3. **交错测量**（A B A B…，顺序逐轮轮换），而不是 A A A B B B，让热漂移均摊到各配置。
4. 每轮之间 `sleep 2~3s`。
5. 多次取**中位数**，同时记录范围；差异小于离散度视为无结论。

命令模板：

```bash
./build/dqm-llama bench models/chat --matmul-mode <mode> --n-predict <N>
```

另有 A/B 对比（内核改造前后）采用：`git stash push -- src/quant.cc` 重建标量版 → 测量 → `git stash pop` 重建 AVX2 版 → 测量，每轮交替，避免两个时段的整体热状态差异。

## 3. 被测代码结构（理解数据的前提）

### 3.1 Linear 的分派

`src/matmul_dispatch.cc:312-334`：

```
LinearDispatch(x, weight, mode)
├── weight 是 F32 Tensor            → LinearDispatchF32(..., mode)      // mode 生效
└── weight 是 QuantizedTensor
      ├── kF32 → LinearDispatchF32(..., mode)                          // mode 生效
      ├── kQ80 → LinearQ80(x, data, shape)                             // 无视 mode
      ├── kQ40 → LinearQ40(...)                                        // 无视 mode
      └── kQ41 → LinearQ41(...)                                        // 无视 mode
```

通用 `MatmulDispatch`（attention 里的 F32 矩阵乘）中，`kThreaded` / `kSimd` / `kThreadedSimd` 全部退回 `MatmulThreaded`，只有 `kNaive` 走单线程 `MatmulNaive`（`:299-309`）。

### 3.2 tied lm_head 被包装成 F32

Qwen2-0.5B 的 GGUF **没有 `output.weight`**，embedding 与 lm_head 共享。loader 的处理（`src/gguf_loader.cc:356-359`）：

```cpp
if (tensor_map.find("lm_head") != tensor_map.end()) {
  model.lm_head = load_weight("lm_head");
} else {
  model.lm_head = ToQuantizedTensor(model.token_embedding);  // type = kF32
}
```

而 `ToQuantizedTensor` 只是把 F32 数据装进 `kF32` 容器（`src/quantized_tensor.cc:55-61`）。因此：

- GGUF 里 `token_embd.weight` 是 Q8_0（约 136 MB）；
- 加载后 `token_embedding` 是 F32（544 MB），`lm_head` 又复制一份 544 MB；
- **lm_head 走的是 F32 分支，是全模型唯一受 `--matmul-mode` 影响的矩阵。**

### 3.3 ParallelFor 的并行门槛

`src/thread_pool.cc:196-202`：`n < n_threads * 16` 时直接串行。默认 20 线程时为 320。tiny 模型的输出维度只有 32 / 86 / 128，达不到门槛。

## 5. 原因分析

### 5.1 AVX2 内核为什么能提升 4.3 倍

旧实现每个权重都要：查 block、算 FP16 scale、标量转换、标量乘加。AVX2 版本每 8 个 int8 一次完成：

```
_mm_loadl_epi64 → _mm256_cvtepi8_epi32 → _mm256_cvtepi32_ps
→ × scale → _mm256_fmadd_ps(x)
```

省掉的不只是乘加，还有逐元素的反量化开销。且累加器跨 block 复用，末尾只做一次水平归约。

### 5.2 AVX2 之前，为什么四个 mode 几乎一样

Q8_0 权重占全模型的绝大多数计算，而 `LinearQ80` 的签名里没有 mode（`src/quant.cc` 中 `LinearQ80(x, weight, weight_shape)`），四个 mode 请求都落到同一份标量内核。唯一有 mode 的 lm_head 只占约 1/10 耗时，差异被 ±15% 的运行波动淹没。

### 5.3 为什么 naive 明显更慢（9 vs 15）

- lm_head 的 F32 分支：naive 是单线程标量；
- attention 里的 F32 矩阵乘：naive 走 `MatmulNaive`，单线程。

两处都失去多线程。

### 5.4 为什么 threaded-simd 相对 threaded 只多约 2%

mode 只改到 lm_head，而 lm_head 是**纯带宽负载**：

- 每次 decode 要流 544 MB 的 F32 权重；
- 计算量约 1.36 亿 MAC/token，AVX2 单核算力按 56 GFLOP/s 估，约 5 ms；
- 但 544 MB 按有效带宽 ~9 GB/s（15.6 t/s × 0.544 GB）算，约 60 ms。

算术只占不到 1/10 的时间，SIMD 加速它几乎没有意义。多线程有效，是因为单线程访存带宽不足，需要多核一起喂 DRAM；带宽用满后，再叠加 SIMD 就没有空间了。

反之，如果 lm_head 是算力瓶颈，`threaded` → `threaded-simd` 应有数倍提升，实际只有 2%，这本身就是带宽瓶颈的证据。

### 5.5 为什么 tiny 模型上 threaded 与 naive 完全相同

tiny 的输出维度（32 / 86 / 128）都低于 `ParallelFor` 门槛 `n_threads × 16 = 320`，直接走串行，所以 threaded 执行的就是 naive 的代码；threaded-simd 同理等于 simd。tiny 上能测到的只有 SIMD 的算术收益（约 +18%）。

### 5.6 噪声与热降频

- 同一配置重复测量可见 3.1–5.7 t/s 的整体漂移，跨轮次出现断层（例如整轮从 ~5.3 掉到 ~3.4），是笔记本持续满载后的热降频 / 功耗墙。
- 因此跨时段比较必须用交错 + 重建的方式（4.1 节），不能用两个时间点各自跑一次。
- WSL 下无法读实时频率，只能靠离散度判断是否受控。

## 6. 局限与后续

1. **tied lm_head 的 4 倍冗余是当前最大瓶颈**：GGUF 里 `token_embd.weight` 本身就是 Q8_0（136 MB），loader 却反量化成 F32（544 MB）并再复制一份给 lm_head。如果让 tied `lm_head` 直接复用 GGUF 的 Q8_0 块（走 AVX2 `LinearQ80`），lm_head 的访存量降到 1/4，decode 有望进一步明显提升。
2. 当前四模式的数字（15.28 / 14.25 / 15.62）主要反映 lm_head 的单/多线程差异；等 lm_head 改成 Q8_0 后，mode 对比预计又会回到“无差别”。
3. 线程数固定为 20（含 E 核与 SMT）；未测试 `--threads 6/12` 等 P 核绑定方案，异构核 straggler 的影响未量化。
4. 尚未覆盖 prefill 的规模化对比（长 prompt 下 attention 占比升高的情形）。
